# dark-store-api

Stateless raw content store for the dARK stack.

## Overview

`dark-store-api` is the default metadata storage backend used by the minter and resolver. It stores and retrieves raw bytes by CID and deliberately does not understand dARK metadata semantics.

- L1/L2 meaning lives in `dark-core-lib`
- L1 is always JSON, but the store only sees raw bytes
- L2 is always stored raw
- schema and media type are modeled in `L1.original_metadata`, not in the store

The service can run on:

- `ipfs_cluster` as the default backend
- `filesystem` as a fallback for local development and tests

## API

| Method | Endpoint | Description |
|--------|----------|-------------|
| `POST` | `/v1/store` | Store raw bytes and return a CID |
| `GET` | `/v1/retrieve/{cid}` | Retrieve raw bytes by CID |
| `GET` | `/v1/status/{cid}` | Get pin / replication status |
| `GET` | `/health/live` | Lightweight process liveness check |
| `GET` | `/health` | Cached storage readiness check |

### Store

```bash
curl -X POST http://localhost:8003/v1/store \
  -H "Content-Type: application/xml" \
  -d '<record><title>Demo</title></record>'
```

Response:

```json
{
  "cid": "bafkreidxvj2rtmmscbwzuss4yx6rpgp434rw2hfufhp4a4t4enb3hi4yd4",
  "size": 42
}
```

### Retrieve

```bash
curl http://localhost:8003/v1/retrieve/bafkreidxvj2rtmmscbwzuss...
```

The response body is raw content bytes. `application/octet-stream` is used as the transport media type; consumers that need richer semantics should read them from L1.

## Configuration

| Variable | Default | Description |
|----------|---------|-------------|
| `STORAGE_BACKEND` | `ipfs_cluster` | Backend type: `ipfs_cluster` or `filesystem` |
| `IPFS_ADD_MODE` | `cluster_proxy` | Write mode: `cluster_proxy` or explicit legacy `ipfs_then_cluster` |
| `IPFS_API_URL` | `http://localhost:5001` | Local IPFS node API endpoint used for `cat`, health, and legacy add mode |
| `IPFS_CLUSTER_API_URL` | `http://localhost:9094` | IPFS Cluster REST API endpoint |
| `IPFS_CLUSTER_PROXY_API_URL` | `http://localhost:9095` | IPFS Cluster Proxy endpoint used by default for writes |
| `IPFS_CLUSTER_MIN_PEERS` | `2` | Minimum visible IPFS Cluster peers required for `/health` to report healthy |
| `IPFS_HEALTH_CACHE_TTL_SECONDS` | `10` | Readiness cache TTL for `/health` |
| `FILESYSTEM_STORAGE_PATH` | `./storage` | Path for filesystem backend |
| `STORE_API_HOST` | `0.0.0.0` | API bind address |
| `STORE_API_PORT` | `8003` | API port |

## Docker stack

The component ships with:

- `Dockerfile`
- `docker-compose.yml`
- `.env.integration` generated by the root installer

In the installed stack:

- host port `8003` exposes `dark-store-api`
- the container joins `dark-net` and `dark-ipfs-store-node`
- Docker healthcheck calls `/health/live`, which does not touch IPFS or Cluster
- `/health` is readiness: it checks local `ipfs0`, local `cluster0`, and visible Cluster peers, with a short cache
- by default, writes go through `cluster0` Proxy (`/api/v0/add?cid-version=1&pin=true`) and Cluster handles replication

## Integration with dARK

- `dark-core-minter-api` publishes L2 raw bytes here and then publishes L1 JSON that embeds `schema`, `media_type`, and `cid`
- `dark-core-resolver-api` reads L1 from blockchain storage, then reads raw L2 from this service and restores the final media type from L1

That separation is intentional: the store stays simple, while dARK metadata semantics stay in the shared core library.
